# Brightech WhatsApp Bot – Backend

Production-ready Node.js backend for the **Brightech Group WhatsApp-style enquiry chatbot**
(`brightech-whatsapp-bot-preview.html`). It reproduces the exact same conversation workflow on the
server, stores everything in MongoDB, and ships with the original chat UI already wired to the API.

* **Stack:** Node.js 18+, Express 4, MongoDB + Mongoose 8, JWT, Joi, Socket.IO, Helmet, CORS, rate limiting, multer
* **Time:** `Asia/Kolkata` by default, timestamps stored in **UTC**, 12-hour / 24-hour display, live server-corrected clock
* **Tested:** 13 engine tests + 38 end-to-end API checks (real HTTP → MongoDB) + 17 MSG91/WhatsApp checks (against a fake MSG91) + a browser-DOM smoke test of the UI

---

## 1. What was built (and the decisions I made)

Your bot is a fixed-rule, no-AI flow. I analysed the HTML and ported **every** menu, option, prompt,
validation rule, navigation command (Go Back / Main Menu / Skip / Continue / End Conversation),
keyword shortcut, the "More options" sub-list, the VFD shortcut and the inactivity prompt
**1:1** into `services/flow/`. No message text was changed.

| Your request | What I did | Why |
|---|---|---|
| "Recreate the exact same workflow" | Flow definitions + engine ported line-by-line (`services/flow/flows.js`, `engine.js`) and covered by tests | Business logic must not change |
| Date picker | The original **7-day list is kept**; a new row **"Pick another date"** opens a real **calendar** (native `<input type="date">`). Backend validates: real date, from tomorrow, within `BOOKING_MAX_DAYS_AHEAD` (90) | You asked for both "don't change the workflow" and "calendar picker" – this satisfies both |
| Live time | Live clock panel (left column) updated every second, **corrected from the server clock**, 12h/24h toggle, timezone selector. Chat timestamps are real, stored as UTC and converted for display | The preview only had bubble timestamps |
| Time slot | The original four slots (Morning / Afternoon / Evening / No preference) are kept – exact hours are still **"To be confirmed"** in your spec | Not invented |
| Users / bots | The UI has no login. Chat visitors become anonymous **customer** users (JWT issued on first visit). **Admins** (JWT + password) manage enquiries/bookings/users/bots | Matches the real workflow; no fake screens |
| Reference number | `BT-PRD-1411-001` format, generated by an **atomic MongoDB counter** (unique across servers). Your notes say the final format is "To be confirmed", so the prefix is configurable (`REFERENCE_PREFIX`) | Preview used a browser counter |
| Files | Stored on server disk (`UPLOAD_DIR`), type/size checked, served through short-lived signed links, deleted when the record is deleted | You did not choose a storage – disk is the default; swapping to S3 only touches `middleware/upload.js` + `services/fileService.js` |
| Channel | Web chat preview (REST + Socket.IO) **and real WhatsApp through MSG91** (section 11). Both use the same engine, database and admin API | You asked for the MSG91 auth key + new number |

> The three questions I asked before building were unanswered, so the above are my defaults. Each is isolated and easy to change.

## 3. Install & run

Requirements: **Node.js ≥ 18**, **MongoDB ≥ 5** (local or Atlas).

```bash
cd backend
npm install
cp .env.example .env            # then edit .env (see below)
npm run seed                    # creates the default bot (+ admin if ADMIN_EMAIL / ADMIN_PASSWORD are set)
npm run dev                     # development (nodemon)   |   npm start   → production
```

Open **http://localhost:5000** – the chat UI is served by the backend itself.

Minimum `.env`:

```env
MONGODB_URI=mongodb://127.0.0.1:27017/brightech_bot
JWT_SECRET=<32+ random chars>      # node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
ADMIN_SETUP_KEY=<any secret>       # enables POST /api/auth/register-admin (leave empty to disable)
```

Everything else has a safe default (see `.env.example`: timezone, rate limits, upload limits, CORS origins …).

Create the first admin either with the seed script (`ADMIN_EMAIL`/`ADMIN_PASSWORD`) or:

```bash
curl -X POST localhost:5000/api/auth/register-admin \
  -H "Content-Type: application/json" -H "X-Setup-Key: <ADMIN_SETUP_KEY>" \
  -d '{"name":"Admin","email":"admin@brightech.example","password":"Str0ngPass99"}'
```

Tests:

```bash
npm test                                   # engine tests, no database needed
MONGODB_URI=mongodb://127.0.0.1:27017/brightech_bot_test npm run test:api   # end-to-end (drops that DB!)
npm run dev   # in another terminal, then:  npm run test:ui   # drives the real UI (jsdom) through a full enquiry incl. calendar + refresh
```

## 4. API overview

All responses share one shape:

```json
{ "success": true,  "data": { }, "message": "optional", "meta": { "page": 1, "limit": 20, "total": 1, "totalPages": 1 } }
{ "success": false, "error": { "code": "DATE_IN_PAST", "message": "Please choose a date from tomorrow onwards.", "details": [ ] } }
```

Auth: `Authorization: Bearer <JWT>`. Customers get their JWT from `POST /api/conversations`.

| Method & path | Auth | Purpose |
|---|---|---|
| `GET /api/health` | – | Liveness + DB state |
| `GET /api/time?timezone=&format=12h\|24h` | – | Server clock (UTC + display) |
| `GET /api/bots/public` | – | Header text, timezone, booking limits |
| **Auth** | | |
| `POST /api/auth/register-admin` | `X-Setup-Key` | Create an admin |
| `POST /api/auth/login` | – | Admin login → JWT |
| `GET /api/auth/me` | any | Current user |
| **Conversations / messages** | | |
| `POST /api/conversations` | optional | Start **or resume** the user's conversation (idempotent). Returns token, history, state, time |
| `GET /api/conversations` | any | Own (customer) / all (admin) conversations |
| `GET /api/conversations/:id` | owner/admin | Full history + state (used after refresh) |
| `GET /api/conversations/:id/messages?afterSeq=&limit=` | owner/admin | Message list |
| `POST /api/conversations/:id/messages` | owner/admin | Send typed text or a tapped option → bot replies |
| `POST /api/conversations/:id/files` | owner/admin | Upload photos/docs/videos (`multipart`, field `files`) |
| `POST /api/conversations/:id/date` | owner/admin | Submit a **calendar date** (`YYYY-MM-DD`) |
| `POST /api/conversations/:id/idle` | owner/admin | "Simulate customer inactivity" |
| `POST /api/conversations/:id/restart` | owner/admin | Archive and start a fresh conversation |
| `PATCH /api/conversations/:id/preferences` | owner/admin | Save timezone + 12h/24h |
| `DELETE /api/conversations/:id` | owner/admin | Delete conversation + messages |
| **Enquiries** | | |
| `GET /api/enquiries/mine` | customer | My enquiries (with booking) |
| `GET /api/enquiries` | admin | List/search/filter (`status, category, q, from, to, sort, page, limit`) |
| `GET /api/enquiries/:id` | owner/admin | One enquiry |
| `PATCH /api/enquiries/:id` | admin | `status`, `adminNotes` |
| `DELETE /api/enquiries/:id` | admin | Delete (+ booking + files) |
| **Bookings (date & time records)** | | |
| `GET /api/bookings` | any | Admin: all · Customer: own. Filters `status, timeSlot, from, to, sort, timezone, timeFormat` |
| `GET /api/bookings/:id` | owner/admin | One booking |
| `PATCH /api/bookings/:id` | owner/admin | `dateKey`, `timeSlot`, `status` (customers: only while `requested`) |
| `DELETE /api/bookings/:id` | owner/admin | Delete |
| **Other** | | |
| `GET /api/activities` | any | Activity history (admin: all, customer: own) |
| `GET/PATCH /api/users/me` | any | My profile |
| `GET /api/users`, `GET/PATCH/DELETE /api/users/:id` | admin | User management (delete cascades) |
| `GET/POST /api/bots`, `GET/PUT/DELETE /api/bots/:id` | admin | Bot management |
| `GET /api/files/:name?t=<signed>` | signed link | Download an uploaded file |

Socket.IO (optional): connect with `io({ auth: { token } })`. Events: `conversation:update` (keeps a customer's other tabs in sync),
`enquiry:created` (admins).

## 5. Data model (MongoDB)

| Collection | Key fields | Indexes |
|---|---|---|
| **users** | `role (customer\|admin)`, `sessionId`, `name`, `email`, `phone`, `company`, `password` (bcrypt, admins only), `timezone`, `timeFormat`, `isActive` | unique sparse `sessionId`; unique sparse `adminEmail`; `phone`; `role+createdAt` |
| **bots** | `slug`, `displayName`, `subtitle`, `timezone`, `timeFormat`, `bookingMaxDaysAhead`, `referencePrefix`, `isActive` | unique `slug` |
| **conversations** | `user`, `bot`, `status`, `state` (engine state), `preferences{timezone,timeFormat}`, counters | `user+status+lastActivityAt`, `bot+createdAt` |
| **messages** | `conversation`, `seq`, `role`, `kind`, `text/head/list/buttons/datePicker/file/quote` | unique `conversation+seq` |
| **enquiries** | `reference`, `conversation`, `submissionNo`, `flowId`, `category`, ordered `answers[]`, `attachments[]`, contact fields, `status`, `adminNotes` | unique `reference`; unique `conversation+submissionNo` (no duplicate submissions); `bot+status+createdAt`, … |
| **bookings** | `enquiry`, `dateKey`, `date` (UTC), `dateLabel`, `timeSlot`, `timezone`, `status` | unique `enquiry` (one per enquiry); `date+status`, `user+date` |
| **activities** | `type`, `user`, `actor`, `conversation`, `enquiry`, `meta`, `ip` | `createdAt`, `user+createdAt`, `type+createdAt` |
| **counters** | atomic sequence for reference numbers | `_id` |

Relationships: user ⟶ conversations ⟶ messages · conversation ⟶ enquiries ⟶ booking · everything ⟶ activities.
Timestamps (`createdAt`/`updatedAt`) are on every collection and are UTC.

Duplicate protection: starting a conversation twice resumes the same one; a submission is idempotent
(`conversation+submissionNo` unique + a per-conversation lock); stale taps are rejected; one booking per enquiry.

## 6. Date & time behaviour

* **Server** – `utils/time.js` (Luxon). Default zone `Asia/Kolkata` (`DEFAULT_TIMEZONE`); every stored timestamp is a UTC `Date`.
* **Display** – the API returns `createdAt` (UTC ISO) **and** `displayTime` in the viewer's timezone/format (`3:45 pm` or `15:45`).
  `PATCH /conversations/:id/preferences` saves the choice, so it survives refresh.
* **Live clock** – `GET /api/time` returns `epochMs`; the UI computes the offset to the device clock and ticks every second, resyncing every 5 min.
* **Booking date** – "tomorrow … +7 days" are generated from the real date in the conversation's timezone each time the list is shown,
  so they never go stale. The calendar accepts tomorrow … `BOOKING_MAX_DAYS_AHEAD` days. Persisted in `bookings` and in the conversation state
  (visible in the "Details captured" panel after refresh).

## 7. Postman

1. Postman → **Import** → `docs/Brightech-Bot.postman_collection.json` (regenerate any time with `npm run postman`).
2. Collection variables: set `baseUrl` (default `http://localhost:5000`). `setupKey` must equal `ADMIN_SETUP_KEY` in `.env`.
3. Run folder **1. Customer chat** top-to-bottom (Runner or one by one). Test scripts store `token`, `conversationId` and
   `botMessageId` automatically; `bookingDate` is recomputed (today + 10 days, IST) before every request.
4. "Upload file(s)" – in the Body tab pick a file for the `files` key (png/jpg/pdf…). At the product-image step only images are accepted.
5. Run **2. Admin** (register → login → list/update enquiries and bookings). Folder 3 is destructive cleanup.

cURL equivalents:

```bash
BASE=http://localhost:5000
R=$(curl -s -X POST $BASE/api/conversations -H 'Content-Type: application/json' -d '{}')
TOKEN=$(echo $R | node -pe 'JSON.parse(require("fs").readFileSync(0)).data.token')
CID=$(echo $R   | node -pe 'JSON.parse(require("fs").readFileSync(0)).data.conversation.id')
curl -s -X POST $BASE/api/conversations/$CID/messages -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"type":"text","text":"Hi"}'
curl -s -X POST $BASE/api/conversations/$CID/files    -H "Authorization: Bearer $TOKEN" -F "files=@nameplate.png"
curl -s "$BASE/api/time?timezone=Asia/Kolkata&format=24h"
```

## 8. Frontend integration (Axios)

The bundled UI (`public/js/app.js`) already does all of this. If you keep your own frontend, copy these:

```js
import axios from 'axios';

const api = axios.create({ baseURL: 'http://localhost:5000/api', timeout: 30000 });
api.interceptors.request.use((cfg) => {
  const t = localStorage.getItem('bt_token');
  if (t) cfg.headers.Authorization = `Bearer ${t}`;
  return cfg;
});
const errorText = (e) => e.response?.data?.error?.message || (e.request ? 'Cannot reach the server.' : 'Something went wrong.');

// 1. start or resume (call on page load → history survives refresh)
const { data } = await api.post('/conversations', { timezone: 'Asia/Kolkata', timeFormat: '12h' });
if (data.data.token) localStorage.setItem('bt_token', data.data.token);
const conv = data.data.conversation;           // render data.data.messages immediately

// 2. typed text
const r1 = await api.post(`/conversations/${conv.id}/messages`, { type: 'text', text: 'Hi' });
// r1.data.data.userMessages / botMessages / state  → render with your typing delay

// 3. tapping a list row or button  (messageId = the bot message that was answered)
await api.post(`/conversations/${conv.id}/messages`, { type: 'choice', text: 'Evening', desc: 'Exact hours: To be confirmed', messageId });

// 4. calendar date (the bot sends a message with `datePicker: { min, max }` → show <input type="date" min max>)
try {
  await api.post(`/conversations/${conv.id}/date`, { date: '2026-11-26', messageId });
} catch (e) { showInline(errorText(e)); }       // 422 DATE_IN_PAST | DATE_TOO_FAR | INVALID_DATE

// 5. files
const fd = new FormData(); files.forEach((f) => fd.append('files', f));
await api.post(`/conversations/${conv.id}/files`, fd);

// 6. 12h/24h + timezone (persisted)
await api.patch(`/conversations/${conv.id}/preferences`, { timezone: 'Asia/Kolkata', timeFormat: '24h' });

// 7. live clock
const { data: t } = await api.get('/time', { params: { timezone: 'Asia/Kolkata', format: '12h' } });
const skew = t.data.epochMs - Date.now();       // then: new Date(Date.now() + skew) every second
```

Rendering a bot message: `text` (+ optional `head`) always; if `list` → button `list.btn` opens a sheet of `list.rows` + `list.nav`;
if `datePicker` → button opens a calendar limited to `min…max`; if `buttons` → one tappable row each.
Only the **latest** interactive message is active. Loading states = disable input / show typing until the promise settles; errors are `error.message`.

To host the UI on another origin set `CORS_ORIGINS` and, before `app.js` loads, `window.BRIGHTECH_API_BASE = 'https://api.example.com'`.

## 9. Security

* **Helmet** (strict CSP: scripts from `'self'` only), **CORS** allow-list (`CORS_ORIGINS`), `x-powered-by` removed
* **Rate limiting:** global, auth (20/15 min), chat (60/min), uploads (30/min) – all configurable
* **Validation:** every body/query is validated with Joi (`stripUnknown`), ObjectIds checked, NoSQL-operator keys (`$…`, `a.b`) stripped
* **Auth:** bcrypt (cost 12), password policy, constant-time login, JWT with issuer/type claims, RBAC + ownership checks on every record
* **Uploads:** extension + MIME allow-list, random file names, size/count limits, never served publicly – only via 1-hour signed links with
  `Content-Security-Policy: sandbox`; non-media types download as attachments
* **Errors:** one handler; internals are never leaked (500 → generic message); secrets only from environment, `JWT_SECRET ≥ 32 chars` enforced at boot
* **Audit:** `activities` collection records starts, flow starts, uploads, date/time picks, submissions, admin edits and deletions

## 10. Production notes

* Run behind HTTPS (nginx / load balancer) and set `TRUST_PROXY=1`, `NODE_ENV=production`, a real `CORS_ORIGINS`.
* The per-conversation lock is in-process. With several Node instances use sticky sessions (Socket.IO needs them anyway) or add a Redis lock/adapter.
* Use a MongoDB **replica set** (Atlas) for durability; the multi-document writes are ordered so a retry is idempotent (unique indexes).
* Back up `UPLOAD_DIR` together with the database, or move uploads to object storage.

## 11. WhatsApp via MSG91

The same bot (same menus, validation, enquiry + booking + reference number) now runs on WhatsApp.
One WhatsApp number = one customer user = one conversation. Enquiries show `channel: "whatsapp"` in the admin API.

### 11.1 What you need in MSG91
1. An MSG91 account with a **WhatsApp Business number integrated** (your new number) – MSG91 panel → WhatsApp.
2. Your **Authkey** (MSG91 panel → API). New keys have **IP security ON → add your server's public IP** to the key's whitelist,
   otherwise every send fails with 401/403.
3. A public **HTTPS** URL for this backend (a server, or `ngrok http 5000` / Cloudflare Tunnel while testing).

### 11.2 Configure the backend (`.env`)
```env
MSG91_ENABLED=true
MSG91_AUTH_KEY=<your authkey>
MSG91_INTEGRATED_NUMBER=919XXXXXXXXX        # digits, country code, no +
MSG91_WEBHOOK_SECRET=<random 16+ chars>
MSG91_LOG_RAW=true                          # keep ON for the first tests, then turn OFF
```
Restart (`npm run dev`). Check: `GET /api/webhooks/msg91/status` (admin token) → `{ "enabled": true, … }`.

### 11.3 Tell MSG91 where to send incoming messages
MSG91 panel → **WhatsApp → Webhook (New) → Create Webhook** → event **"On Inbound Request Received"**.

* URL: `https://YOUR-DOMAIN/api/webhooks/msg91?secret=<MSG91_WEBHOOK_SECRET>`
* Method POST, content type JSON, body (paste this; every field is optional – extra ones are ignored):

```json
{
  "requestId": "{{requestId}}",
  "uuid": "{{uuid}}",
  "customerNumber": "{{customerNumber}}",
  "integratedNumber": "{{integratedNumber}}",
  "eventName": "{{eventName}}",
  "direction": "{{direction}}",
  "contentType": "{{contentType}}",
  "content": "{{content}}",
  "messages": "{{messages}}",
  "interactive": "{{interactive}}",
  "button": "{{button}}",
  "requestedAt": "{{requestedAt}}"
}
```
Now send "Hi" to your WhatsApp number from another phone → the main menu list should arrive.

| Topic | Behaviour |
|---|---|
| Lists / buttons | Sent as WhatsApp interactive list / reply-button messages. If MSG91 rejects that JSON, the bot **automatically sends a numbered text menu** (reply `1`, `2`… or the option name). Force this with `MSG91_INTERACTIVE=false`. |
| WhatsApp limits | Max 10 rows per list (the date list drops the Go Back / Main Menu rows and adds a hint – typing `Go Back` / `Main Menu` always works), row title 24 chars, button title 20 chars, 3 buttons, body 1024 chars (longer text is sent as a normal message first). |
| Calendar | WhatsApp has no date picker, so "Pick another date" asks the customer to **type `DD/MM/YYYY`** (validated: from tomorrow to +90 days). |
| Photos / documents / videos | Downloaded from the URL MSG91 provides, type/size checked, stored like web uploads. Only hosts in `MSG91_MEDIA_HOSTS` are allowed (SSRF guard). |
| Re-delivery | Each webhook is de-duplicated by its `uuid`, and acknowledged immediately (processing happens in the background). |
| 24-hour rule | Free-form replies work only inside WhatsApp's 24 h customer-service window. Messaging a customer first needs an approved template (not used by this bot). |
| Inactivity prompt | Web-preview only. |

### 11.5 If something does not work (everything MSG91-specific lives in `services/msg91/`)
| Symptom | Check / fix |
|---|---|
| Nothing arrives, no log line | Webhook URL/secret wrong (401), or tunnel not running. Test: `curl -X POST "https://YOUR-DOMAIN/api/webhooks/msg91?secret=…" -H 'Content-Type: application/json' -d '{"uuid":"t1","customerNumber":"919876543210","direction":"inbound","contentType":"text","content":"{\"text\":\"Hi\"}"}'` |
| Log shows `webhook ignored: no text/media in payload` | MSG91's payload shape differs. Read the `[MSG91 raw inbound]` line (`MSG91_LOG_RAW=true`) and adjust **`parser.js`** (`pickReply` / `pickMedia`). |
| `MSG91 401/403` on send | Wrong `MSG91_AUTH_KEY`, or server IP not whitelisted in MSG91. |
| Menu arrives as plain numbered text | MSG91 rejected the interactive JSON (see the WARN log with MSG91's error). Adjust **`formatter.js`** to the schema in MSG91's *Interactive WA with List/Buttons* docs, or keep the text fallback. |
| "media host … is not in MSG91_MEDIA_HOSTS" | Add that host to `MSG91_MEDIA_HOSTS`. |
| Want to test without sending | `MSG91_DRY_RUN=true` prints each outgoing payload. |

Files you may need to edit: `parser.js` (incoming format) · `formatter.js` (outgoing list/button JSON) · `client.js` (endpoint/headers) · `media.js` (file download).
Test everything offline with a fake MSG91: `npm run test:msg91`.
